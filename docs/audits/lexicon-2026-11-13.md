# Supplied Tamil lexicon audit — 2026-11-13

## Assessment

The bundle is a useful intake collection with good primary-table referential
integrity. It is not yet a reviewed, distributable dictionary or a reliable
morphology resource. Professional readiness requires traceable source records,
sense-level editorial work, explicit data contracts, and a reproducible index
that returns every matching lexical entry.

This audit did not change any of the 12 supplied files. All intake SHA-256
hashes still match. No lexicon data was wired into a runtime or release.

The owner reports that publicly accessible online sources were combined using
Python extraction scripts. Exact URLs, source snapshots, extraction scripts,
and terms were not supplied in this bundle. Whether particular annotations
were generated, inferred, copied, or manually reviewed remains unresolved.
The owner's statement that no licensed work was used is recorded as an owner
assertion; this audit has not independently established redistribution rights.

## Scope and evidence

All 11 CSVs were parsed, not merely sampled. The audit checked UTF-8 decoding,
record width, IDs, empty fields, normalization and control scalars, categorical
values, primary foreign keys, duplicated master fields, and sense counts.
There are 92,616,773 source bytes including the binary index.

## Findings

### 1. Primary structural integrity is good

- Every CSV decoded as UTF-8 and had consistent record widths.
- No repeated primary IDs were found within the individual CSVs.
- All primary meanings resolve to existing entries; all primary relationship
  endpoints resolve; stored endpoint spellings match the referenced entries.
- Every primary entry has a meaning record. Sense numbers are unique within
  each entry; master sense counts match the supplied meaning rows.
- Shared entry fields in master and lemmas agree. There are no repeated
  `(headword, part_of_speech)` pairs in the primary lemma table.

These checks establish structural consistency, not correctness of definitions,
POS assignments, etymologies, pronunciation, or semantic links.

### 2. Provenance and rights are not traceable enough for publication

Primary entries and senses have no source-reference columns. Some secondary
tables have source labels, but no source registry, source snapshots, retrieval
dates, edition/page/entry locators, or license records accompany them.

Observed labels include `TVA_KALAICHOL` (117,121 technical records),
`sorkuvai_technical` (3,361 technical records), `SRC-OXFORD-APPLE` (2,187
phrase records), and `Tamilcube Bilingual Dictionary` (2,981 phrase records).
These labels are leads, not verified attributions. Other source-code values
name transformations such as compound deconstruction rather than publications.

Build a source registry and connect evidence to entries, senses, examples,
relations, and annotations. Preserve extraction versions and any transformation
history. Distinguish source access, source attribution, and permission to
redistribute. Public online availability alone does not establish public-domain
status; see [WIPO's copyright FAQ](https://www.wipo.int/en/web/copyright/faq-copyright).
This report makes no source-specific legal determination.

### 3. Verification labels overstate the supplied evidence

All 44,229 primary entries, 63,633 meanings, and 19,849 relationships are marked
`verified`. All entry and relationship confidence values are 1.0. There are no
reviewer identities, review dates, methods, evidence links, or calibration rules.

Preserve these as imported assertions. In the curated dataset, track separate
states for successful import, source verification, linguistic review, and
release eligibility. Track annotation origin and reviewer at the field or
assertion level. Do not infer human review or AI generation from these values.

### 4. Sense extraction and language separation need editorial repair

- 46,529 meaning records have no Tamil meaning; 34,188 lack a Tamil definition.
  Missing fields can be legitimate for a bilingual wordlist, but must be
  documented rather than presented as complete bilingual definitions.
- 13,894 English meaning fields contain Tamil scalars. Some contain bilingual
  definitions, grammatical abbreviations, citations, or other dictionary text.
- 51,835 English meaning fields exactly duplicate their definition field.
- 4,278 definition records match a conservative pattern containing both `1.`
  and `2.` numbered segments. This is a review queue, not a proven count of
  incorrectly split senses: quotations and nested senses can also match.
- All 120,482 technical records have both definition fields empty. Their
  English terms remain useful translation equivalents.

Retain source text, then distinguish definitions, glosses, translation
equivalents, examples, citations, etymology, grammatical notes, and senses.
Resolve nested and historical homograph structures against source entries.
Do not blindly split on punctuation or generate missing definitions as facts.

### 5. The supplied index returns one ID per spelling

An isolated Rust `fst` 0.4.7 reader successfully opened and checksum-verified the
binary. All 43,831 keys match primary spellings and every stored value resolves
to an entry with that spelling. However, 389 spellings have multiple entries;
398 entry IDs are not directly represented among index values. For example,
the U+0B85 spelling has entries `1` and `2`, but its index value is `1`.

This is incomplete for a lookup that relies solely on the stored ID. Use
`spelling -> posting-list offset -> all entry IDs`, or an equivalent
one-to-many design. A caller that separately expands the spelling could recover
these records, but no such consumer is supplied. Build exact and folded search
indexes separately; folding collisions must retain every candidate.

The original index builder, settings, and manifest are absent. Reading the
binary does not prove that it can be reproduced from the supplied sources.

### 6. Unicode normalization is mostly clean; orthography needs separate checks

Primary headwords are NFC and have no detected control/format scalars.
The meaning CSV contains 9 non-NFC cells and 2 cells containing U+FEFF;
the duplicated master contains 7 non-NFC cells and 2 U+FEFF cells. These are
cell counts across overlapping tables, not counts of independent errors.
Each of those two files also has 6 cells with outer whitespace.

NFC alone does not prove valid Tamil orthography. Entry `4848` contains
`\u0ba4\u0bc1\u0bbe` (two vowel signs on the consonant); the current Rust
inspector classifies that cluster as `other`. Preserve it for source comparison.
Across all 44,229 master rows, 63 stored grapheme counts and 63 stored duration
values disagree with current Rust calculations. Several examples involve
KSHA tailoring; disagreement may reflect different conventions as well as
bad input. Resolve the contract before changing values.

Keep original spelling, curated NFC spelling, search fold, and source correction
history distinct. Preserve intentional format controls with explicit review.
Generate deterministic derived counts through the shared Rust engine with a
recorded algorithm version. Do not turn imported Punarchi prose into rules.

### 7. Linguistic categories and regional coverage need explicit contracts

Relationships mix `SYNONYM` and `synonym` and mix directed/bidirectional
representations. Domains mix `General`/`general`, inconsistent veterinary labels,
and WordNet-style labels. Define documented code lists with display labels.

The primary data has 39,196 noun entries and only 3,653 verbs. Root equals
headword for 42,786 entries; this is not evidence of usable morphological
decomposition. All entries have IPA, but no transcription convention,
dialect, attestation, or generator metadata is supplied. Verb classes `1`–`7`
need a named classification system and source; grammatical categories should
not be forced into unsupported one-to-one mappings.

The dialect table contains Kongu 469, Madras Baashai 342, Jaffna 310, General
Spoken 106, Gen-Z / Cinema 39, Madurai 34, and Nellai 23. Geographic varieties,
register, and social/media usage must be different fields. There are no explicit
Batticaloa, Vanni, or Up-Country labels in this table. That means coverage is
undocumented, not that those varieties have no relevant vocabulary. Keep
coverage gaps visible; never fill them by inference from another region.

542 relationship targets have spellings shared by multiple primary entries.
Their ID references are structurally valid, but sense/POS selection needs
review. Synonymy is often sense-specific; retain typed entry or sense endpoints
and supporting evidence.

## Recommended target and order of work

Use versioned UTF-8 CSV tables plus machine-readable schema and TOML metadata
in the project's canonical `lexicon/` area after review. The source snapshot
stays unchanged in `data/sources/`. Start with the CLDF Dictionary separation
of entries, senses, examples, and sources; add documented Tamil-specific
annotations and provenance. CLDF provides a practical CSV interoperability
target ([official model](https://cldf.clld.org/v1.0/terms.html)). Map exports to
[TEI Lex-0](https://lex-0.org/) when needed for dictionary exchange. This is a
design recommendation, not a claim that this bundle already conforms.

| Priority | Work | Acceptance condition |
|---|---|---|
| P0 | Recover source URLs, extraction scripts, snapshots, and terms | Every releasable assertion has a traceable source and documented reuse basis; unresolved material remains intake-only |
| P1 | Specify entries, forms, senses, examples, relations, sources, and review records | Stable opaque IDs, explicit foreign keys, controlled labels, missing-value rules, and legacy-ID mapping; POS corrections never change identity |
| P1 | Curate a small representative pilot before bulk conversion | Include homographs, verbs, mixed senses, technical MWEs, regional entries, and problematic scalars; every change has evidence |
| P1 | Automate validation and editorial queues | Structural errors fail; unresolved linguistic assertions are visible; Unicode corrections are reversible; originals remain hash-identical |
| P2 | Import approved data with complete accounting | Every source record maps to curated records, an explicit merge, or a documented quarantine; no silent losses |
| P2 | Build reproducible Rust lookup indexes and package profiles | Every spelling returns all entries; identical inputs produce identical bytes; manifests record source/schema/tool versions and hashes |
| P2 | Expose a bounded toolkit API | Sourced escaped golden cases precede Rust lookup code; Python, WASM, and Dart share the dispatcher and pass parity |
| P3 | Expand reviewed annotation and coverage | Source-backed pronunciation, morphology, usage examples, corpus frequencies, and regional coverage; claims match actual review |

Keep core dictionary, terminology, names/taxa, and regional extensions as
selectable data packs so a small WASM consumer need not embed the entire source
collection. Treat the master CSV as a generated export of curated tables.
SQLite can be an optional generated inspection/export format, rather than
another independently edited source. Do not add a new linguistic engine,
guessed morphology, or a new public crate as part of data cleanup.

First runtime scope should be exact entry lookup and retrieval of reviewed
senses, with explicit region/register filters. Add folded/prefix lookup only
after their matching semantics and collision behavior are specified. Spell
checking, inflection, Punarchi, and dialect transformation need separate
linguistic contracts; a dictionary lookup does not establish those capabilities.

## Reproduction and checks

- `tools/audit_lexicon_source.py --output <path>` reproduces structural metrics
  using Python's standard library. `--runtime-check` also invokes the local
  native Rust adapter; `--fst-keys <tsv>` compares an exported key/value stream.
- Audit invocation: `.venv/Scripts/python.exe tools/audit_lexicon_source.py
  --output docs/audits/lexicon-2026-11-13.metrics.json --runtime-check
  --fst-keys target/lexicon-fst-keys.tsv`.
- The FST stream was obtained by an isolated scratch Cargo project under
  `target/lexicon-fst-audit/`, pinned to `fst = "=0.4.7"`, calling
  `Map::new`, `as_fst().verify()`, and `stream()`; it exports UTF-8 key and ID
  pairs as TSV. It does not change workspace manifests or the workspace lock.
- Source SHA-256 comparison: all 12 files passed.
- Repository Unicode/schema gate passed with 36,131 active golden vectors.
  That existing gate does not inspect CSV contents, so this audit's CSV
  checks are separate. No new golden suite was activated.
- `agent-post-edit` passed via `.venv/Scripts/python.exe tools/tasks.py
  agent-post-edit`, including Rust formatting, Unicode/schema checks, 65 release
  source-copy checks, and locked workspace check. Log:
  `target/lexicon-audit-post-edit.log`. `git diff --check` also passed.
- No full parity or archive gate is claimed: no runtime behavior changed.

The audit covers every row structurally and selected content examples. It is
not a dictionary-wide linguistic review, source authenticity review, rights
clearance, or certification of a standards-compliant publication.
